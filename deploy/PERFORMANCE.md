# Проверка отклика и детализации

Нулевой задержки и отсутствия артефактов при любых сценах нельзя гарантировать.
Нужно проверить маршрут и оба ПК. Из облачной среды разработчика нельзя измерить
маршруты вашей домашней сети без отчётов, собранных на ваших машинах.

## Для текущего соединения через Tailscale

1. Обновите ОБА клиента до 0.4.0. Оставьте «Разрешать маршруты Tailscale / Radmin»
   включённым, маршрут «Авто». Не выбирайте «Только TURN» для первого сравнения.
2. Создайте новое приглашение, обменяйтесь новым ответом и примените его у хоста.
   Общая служба регистрации для этого ручного режима не нужна.
3. Во время трансляции на обоих ПК нажмите «Качество и сеть → Проверить путь Tailscale».
   Если у потока выбран адрес Tailscale, клиент запустит официальный CLI Tailscale
   и покажет прямой путь либо DERP. Нужна установленная программа Tailscale.
   Если поток выбрал другой интерфейс, отчёт так и сообщит, не приписывая ему VPN.
4. Соберите 30–60 секунд движения в одной сцене, включая повороты камеры. Затем
   «Сохранить отчёт в файл». Файлы лежат в папке данных Tandem, в reports.
5. Повторяйте в одной сцене с одинаковым разрешением. Сначала ручной 1080p/60,
   H.264, 45 Мбит/с; затем авто; затем H.265/AV1 при аппаратной поддержке. Режим
   120 FPS сравнивайте после стабильных 60. Увеличение битрейта допустимо только
   при запасе канала, без роста очереди/потерь. Не делайте вывод по статичному меню.

Ручной вариант проверки в PowerShell, если используется старый клиент:

```powershell
& "$env:ProgramFiles\Tailscale\tailscale.exe" status
& "$env:ProgramFiles\Tailscale\tailscale.exe" ping --c=5 --timeout=2s --until-direct=false 100.X.X.X
```

Замените 100.X.X.X на Tailscale IP друга. `direct` или пинги через IP:порт
показывают прямой путь на момент замера; `relay`/`DERP(регион)` — ретранслятор.
Первый пинг может идти через DERP, а следующие стать прямыми. Клиент учитывает
последний путь и отдельно показывает RTT всей серии, включая прогрев.

## Что действительно можно изменить

- Если Tailscale идёт через DERP: сначала проверьте доступность прямого UDP и NAT
  на обоих ПК по официальной документации Tailscale. Нельзя назначить произвольный
  маршрут у провайдера из приложения. Сервер «в том же городе» без теста обоих
  направлений не гарантирует меньший RTT.
- Если потери/очередь растут: снизьте нагрузку на канал, сравните Ethernet и Wi-Fi,
  исключите параллельную передачу больших файлов, проверьте роутер под нагрузкой.
  Больший лимит битрейта при этом может ухудшить отклик.
- Если сеть быстрая, а кодирование или декодирование медленные: проверьте настоящий
  аппаратный кодек на обоих ПК, драйвер и запас ресурсов GPU, снизьте FPS/разрешение.
- Если при быстрой сети картинка сильно сжата: сравните битрейт, меньший FPS при
  том же разрешении, аппаратный H.265/AV1. QP — косвенный признак, а не оценка
  картинки. Для разных кодеков шкала различается.
- Если велик буфер сверх сетевого минимума: сравните поток без системного звука,
  так как синхронизация аудио/видео может добавлять буфер. Не отключайте звук
  автоматически: это диагностическое сравнение.

## Протоколы и конвейер

Обычный путь: игра → захват → кодировщик GPU/CPU → WebRTC/SRTP → выбранный
сетевой маршрут → декодирование → буфер/композитор → монитор.
Ввод идёт обратно по каналу данных; задержка видео не равна задержке управления.

UDP избегает ожидания повторной передачи предыдущих пакетов, характерного для
TCP. WebRTC сам обеспечивает защиту, восстановление и управление перегрузкой.
Tailscale — дополнительный слой: внутренний UDP может пройти через DERP, поэтому
название UDP на видеопотоке недостаточно. TURN — ещё один возможный посредник.
Тестировать нужно реально выбранный путь и стабильность RTT, а не только название.

Нативный DXGI/WGC → NVENC с low/ultra-low-latency tuning, небольшим VBV,
контролем очереди и аппаратным декодированием даёт больше управления задержкой,
чем текущая оболочка WebRTC. Эти параметры NVENC не становятся доступными через
RTCRtpSender.setParameters; прямой нативный конвейер пока не внедрён. Наличие
RTX не доказывает, что именно NVENC использован в конкретном потоке.

## Ограничения замера

Окно — до 60 секунд; p95 показывает 95-й процентиль имеющихся отсчётов.
Показатели WebRTC опциональны. Неизвестные значения не считаются нулём.
От последнего пакета кадра до композитора — браузерная часть пути, не фактическое
время появления пикселя на мониторе. Полную задержку ввода корректно измерять
специальным внешним тестом, например высокоскоростной камерой с видимым событием.
Не складывайте RTT, буфер и время обработки как точное измерение input-to-photon.

Windows/Tailscale-команды в этой среде проверяются по фикстурам, а не на ваших
ПК. Два клиента WebRTC проверяются в Linux через loopback TURN/TCP. Настройки
сетевых интерфейсов, роутера, брандмауэра и Tailscale диагностикой не изменяются.
